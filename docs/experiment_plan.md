# Experiment Plan

## Common Setup

Create a manually annotated evaluation split with timestamps, speaker labels, overlap labels, transcript text, topics, decisions, and action items. Report aggregate metrics and separate results for low- and high-overlap regions.

**Synthetic data** can be generated via `src/data_synthesis.py` to produce controlled two-speaker overlap mixtures with known ground-truth labels (overlap duration, SNR, speaker segments). This is useful for pre-evaluation calibration before manual annotation.

## Experiment 1: Overlap Routing

Compare predicted `low_overlap_cluster` and `high_overlap_candidate` routes with manual overlap labels.

**Metrics** (implemented in `src/evaluation.py` — `evaluate_overlap_routing()`):

- **Accuracy**: `(TP + TN) / total`
- **Precision**: `TP / (TP + FP)`
- **Recall**: `TP / (TP + FN)`
- **F1**: `2 * precision * recall / (precision + recall)`

Positive class = `high_overlap_candidate`. Report the downstream cost/quality trade-off at different overlap thresholds.

**Detector options** (implemented in `src/overlap_detector.py`):
- pyannote OSD (requires `HF_TOKEN` and `pip install pyannote.audio`)
- Energy fallback (always available, max score 0.39)

**Status:** Infrastructure ready. Pyannote adapter and energy fallback implemented. Annotated evaluation split pending.

## Experiment 2: High-overlap Candidate Generation

Compare candidate outputs with forced single-output transcription.

**Metrics** (partially implemented — `evaluate_overlap_routing()` and `speaker_attribution_accuracy()` in `src/evaluation.py` cover related aspects):

- **Oracle candidate WER**: best WER among top-K candidates vs reference
- **Top-1 WER**: WER of the highest-confidence candidate
- **Speaker-hypothesis coverage**: fraction of segments where at least one candidate has the correct speaker
- **Candidate usefulness**: human rating of whether useful information survives ambiguous overlap

**Candidate generation baseline** (implemented in `src/high_overlap.py` and `src/candidate_generator.py`): keeps the high-overlap main record mixed/empty and stores candidates generated by faster-whisper multi-decode settings (beam size, temperature, language). If faster-whisper is unavailable, explicit fallback candidates preserve the same uncertainty schema.

**Status:** Candidate interface implemented. Oracle/top-1 WER and human-rated usefulness require manual annotation.

## Experiment 3: Metadata-aware LLM Post-processing

Compare three LLM input configurations:

1. Plain transcript + LLM
2. Transcript + speaker labels + LLM
3. Transcript + speaker labels + overlap/confidence metadata + LLM

**Metrics:**
- Correction quality (WER between raw and corrected transcripts)
- Speaker-attribution accuracy (via `speaker_attribution_accuracy()` in `src/evaluation.py`)
- Uncertainty-preservation quality (are uncertain segments still marked uncertain?)
- Decision extraction accuracy
- Action-item extraction accuracy

**LLM integration** (implemented in `src/llm/event_extractor.py`): currently uses deterministic fallback; Gemma client interface is ready for real LLM connection.

**Status:** LLM event extraction infrastructure implemented. Metadata-input ablation requires real LLM integration and manual evaluation.

## Experiment 4: Episodic Memory QA

Compare three QA approaches:

1. Normal summary-based QA
2. RAG over plain transcript
3. Speaker-aware Episodic Memory QA

**Metrics:**
- QA accuracy (factual correctness)
- Speaker-specific retrieval accuracy
- Action-item retrieval precision/recall
- Cross-meeting recall
- Evidence hit rate (does the answer cite correct segments?)

**Memory infrastructure** (implemented in `src/memory/episodic_store.py` and `src/memory/retriever.py`):
- Episode creation from evidence segments
- atomic JSON persistence with meeting-level replacement
- BM25 + embedding hybrid retrieval with importance, recency, and overlap-aware scoring
- QA response format with evidence, speaker, timestamp, confidence

**Status:** Storage, hybrid retrieval, and baseline QA implemented. Formal QA evaluation and embedding-model comparison remain pending.

## Experiment 5: Hallucination and Evidence Evaluation

Evaluate whether answers, decisions, and action items are supported by timestamped evidence.

**Metrics** (interface defined in `src/evaluation.py` — `evaluate_evidence_support()`, currently stub):

- Evidence precision: fraction of cited evidence that is correct
- Evidence recall: fraction of correct claims that cite evidence
- Unsupported-claim rate: fraction of claims with no supporting evidence
- Hallucination rate: fraction of claims not found in any source segment
- Confidence calibration: how well confidence scores correlate with correctness

**Status:** Metric interfaces defined (stub). Formal experiment requires manual annotation of evidence-support relationships.
