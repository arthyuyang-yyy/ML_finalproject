## 先理解几个核心概念

### Evidence 是什么

Evidence 是系统保存的一条“可回查证据”。它不仅有转写文本，还包括说话人、时间戳、置信度、
重叠分数、候选解释和音频片段路径。

简单说，普通摘要只告诉用户“会议决定了什么”，Evidence 还告诉用户“这个结论来自哪一段音频，
是谁说的，系统有多确定”。

### 重叠路由是什么

会议中有些片段只有一个人说话，有些片段会出现抢话或多人同时讲话。系统先计算
`overlap_score`，再决定片段走哪条处理路径：

- `low_overlap_cluster`：按较稳定的单人语音处理；
- `high_overlap_candidate`：保留多个候选和不确定性，不强行给出唯一答案。

路由阈值过高会漏掉很多真实重叠，阈值过低则会把普通语音送入更昂贵的高重叠路径。因此阈值必须
通过人工标注数据校准，不能只凭经验选择。

### 多候选为什么重要

高重叠语音往往没有唯一可靠转写。如果系统强行选择一个结果，后续事件抽取和问答可能把错误内容
当成事实。多候选的目标不是让结果看起来更多，而是避免系统在不确定时假装确定。

### Episodic Memory 是什么

Episodic Memory 是按会议事件组织的记忆，例如某个决定、行动项或未解决问题。每条记忆必须绑定
原始 Evidence。它与普通摘要的区别是：摘要适合阅读，但容易丢失来源；Episodic Memory 适合检索、
问答和追溯。

### 消融实验是什么

消融实验就是只改变一个关键设计，然后比较结果。例如：

- 不保留候选，与保留候选相比是否更容易出错；
- 只给 LLM 纯文本，与给完整 Evidence 相比是否更容易编造；
- 使用 Transcript RAG，与使用 Episodic Memory RAG 相比是否更难找到正确证据。

消融实验用来证明项目中的设计确实有价值，而不只是“代码可以运行”。

## 推荐执行顺序

后续任务应按下面的顺序推进。人工标注集是多个实验的共同前置条件，应优先完成。

## 阶段 A：建立统一人工标注评估集

### 为什么先做

没有人工真值，就无法判断重叠检测、转写、事件抽取和问答到底对不对。当前仓库中的种子标注适合
验证实验脚本，不足以支撑最终报告结论。

### 应该怎么做

1. 选取真实多人会议音频，优先包含单人讲话、轻度重叠、严重重叠、中英文混合和明确行动项。
2. 按会议划分训练/开发/测试集，不能把同一会议的片段同时放入不同集合。
3. 从正式 Pipeline 导出 VAD 片段和 `evidence_segments.json`。
4. 为片段标注以下真值：
   - 是否重叠，以及重叠程度；
   - 正确转写；
   - 正确说话人；
   - decision、action item、deadline、open question 和 uncertainty；
   - 每个事件对应的 Evidence ID；
   - QA 问题、参考答案和支持答案的 Evidence ID。
5. 至少安排两人标注一部分相同样本，检查分歧并统一标注规则。
6. 保存数据来源、标注说明、划分方法和版本号，保证实验可以复现。

### 需要产出

- 人工标注规范；
- 按会议划分的数据清单；
- 可被实验脚本直接读取的 JSON 标注；
- 标注质量检查记录。

### 完成标准

- 测试集在实验前固定，不根据实验结果反复调整；
- 每个正式指标都能找到对应人工真值；
- 标注数据来自真实 Pipeline 输出，而不是只使用手写示例。

## 阶段 B：完成 Step 7b 重叠路由阈值校准

### 为什么要做

默认阈值 `0.4` 只是保守初始值。仓库已有固定窗口、OSD-only 的探索性实验，但正式 Pipeline 使用
VAD 片段和融合分数，两者的分数含义不同，所以不能直接把探索性阈值替换进正式 Pipeline。

### 应该怎么做

1. 使用正式 `run_meeting_pipeline` 相同的 VAD 片段。
2. 使用正式 Pipeline 相同的融合 `overlap_score`，不要只使用 OSD 分数。
3. 在开发集上扫描多个阈值，例如 `0.05` 到 `0.60`。
4. 对每个阈值计算 accuracy、precision、recall 和 F1。
5. 同时记录成本与质量：
   - 有多少片段进入高重叠路径；
   - 运行时间增加多少；
   - 高重叠召回率是否提高；
   - 普通片段被误送入高重叠路径的比例。
6. 在固定测试集上只评估最终选择的阈值。

### 需要产出

- 阈值扫描结果表和曲线；
- 默认阈值与校准阈值对比；
- 选择最终阈值的理由；
- 可复现命令、配置和数据划分。

### 完成标准

- 校准使用正式 Pipeline 的 VAD 片段和融合分数；
- 最终阈值由开发集选择，并在独立测试集报告；
- 报告不仅有 F1，还说明计算成本和误路由代价。

## 阶段 C：评估高重叠多候选和语音分离

### 为什么要做

项目的核心主张之一是：高重叠片段保留候选比强制输出一个转写更可靠。现在 NMF、SepFormer 和
多参数解码路径已有代码，但仍缺少真实音频上的正式质量比较。

### 应该怎么做

对相同高重叠测试片段比较：

1. 强制单一 ASR 输出；
2. 直接多参数解码候选；
3. NMF 分离后分别 ASR；
4. SepFormer 分离后分别 ASR。

报告：

- Top-1 WER：系统最优先候选的错误率；
- Oracle WER：所有候选中最好候选的错误率；
- WER reduction：保留候选后理论上能减少多少错误；
- Speaker coverage：候选是否覆盖正确说话人；
- 候选数量、运行时间和失败率；
- 人工判断候选是否保留了有用信息。

### 完成标准

- 所有方法使用相同测试片段和相同评分方式；
- 高重叠记录仍保持不确定性，不因分离失败退化成虚假的唯一事实；
- 报告模型质量和额外计算成本。

## 阶段 D：完成 Step 16b 结构化事件抽取对比

### 为什么要做

Step 16a 已有独立规则基线，但还不能证明 Evidence 约束 LLM 比规则或普通 LLM 更好。默认无 LLM
Pipeline 当前仍使用通用 fallback，因此实验时应明确区分“规则基线”和“Pipeline fallback”。

### 应该怎么做

在同一批人工标注会议上比较：

1. 规则抽取器；
2. 只读取纯转写的普通 LLM；
3. 读取完整 Evidence 的约束 LLM。

三种方法必须使用相同事件类型和输出 Schema。评估：

- decision、action item、deadline、open question 的 per-type precision、recall、F1；
- Evidence 引用是否正确；
- owner 是否有证据支持；
- 高重叠不确定性是否被保留；
- 无支持声明和幻觉比例；
- 非法 JSON 或校验失败率。

### 完成标准

- 三种方法使用完全相同的会议和人工真值；
- LLM 输出经过现有 validator，非法或无证据事件不能直接计为正确；
- 报告每类事件结果，不只报告总体平均值。

## 阶段 E：完成 Step 20 QA 对比

### 为什么要做

项目不仅要生成记忆，还要证明 Episodic Memory 能让问答更准确、更可追溯。

### 应该怎么做

准备覆盖以下类型的问题：

- 谁负责某项任务；
- 某个决定是什么，为什么做；
- 有哪些未解决问题；
- 哪些内容仍然不确定；
- 某个说话人在什么时间说了什么；
- 跨会议是否出现相关决定或行动项。

比较三种方法：

1. Summary-only QA；
2. Transcript RAG；
3. Episodic Memory RAG。

模板回答和 LLM 回答应分开记录。LLM 只能作为答案组织器，不能绕过检索器读取全部会议内容。

报告：

- 答案正确率；
- Evidence 命中率；
- 时间戳引用率；
- 说话人和行动项检索准确率；
- 无支持声明率和幻觉率；
- 证据不足时的正确拒答率。

### 完成标准

- 每个事实性回答都可以追溯到真实 Evidence ID 和时间戳；
- 三种方法使用相同问题集；
- 对无法回答的问题，错误编造会被计入失败。

## 阶段 F：完成真实证据与不确定性评估

### 为什么要做

当前证据评估基础设施和种子实验已经存在，但种子结果只能证明脚本可运行，不能作为最终论文数字。

### 应该怎么做

1. 从真实 Pipeline 输出中抽取回答、事件和高重叠候选。
2. 人工标注正确支持证据、答案是否正确、哪些片段确实不确定。
3. 运行现有指标：
   - evidence precision、recall、F1 和 hit rate；
   - unsupported claim rate 和 hallucination rate；
   - uncertainty preservation 和 collapse rate；
   - candidate usefulness；
   - 文本相似度支持指标。
4. 传入完整 `source_evidence_ids`，避免把“存在但不是金标”的证据误判为不存在。
5. 每次修改指标实现或标注后重新生成结果表，避免结果文件与代码不一致。

### 完成标准

- 正式结果来自真实 Pipeline 输出；
- 标注、代码、结果表和运行命令对应同一版本；
- 报告清楚区分错误引用、无支持声明和真正不存在的证据引用。

## 阶段 G：完整验证 Gradio Demo

### 为什么要做

单元测试只能验证组件逻辑。最终演示还需要确认用户真的可以上传音频、查看候选、播放证据并完成
问答。

### 应该怎么做

1. 安装 `requirements-demo.txt` 和演示需要的可选依赖。
2. 使用一段固定演示音频完整运行 Pipeline。
3. 手动检查五个区域：
   - 上传和运行；
   - 时间线；
   - 高重叠候选与音频播放；
   - Meeting Memory；
   - Evidence-cited QA。
4. 记录运行环境、启动命令、演示音频和已知限制。

### 完成标准

- 五个区域均可实际操作；
- Evidence 音频路径可播放；
- 问答引用与界面展示的证据一致；
- 演示流程可以由其他组员按文档复现。

## 每项正式实验都应遵守的规则

1. **先固定数据，再看测试结果。** 不要根据测试集结果反复调整阈值或划分。
2. **每次只比较一个主要变量。** 否则无法解释性能变化来自哪里。
3. **保存配置和随机种子。** 包括模型名、版本、阈值、提示词和数据划分。
4. **同时报告质量与成本。** 更准确但慢很多的方法，需要明确说明代价。
5. **失败结果也要记录。** 例如模型无法加载、分离失败或输出非法 JSON。
6. **不把 fallback 质量当作真实模型质量。** Mock ASR 和手写种子集只用于验证流程。
7. **不把探索性实验当作最终结论。** 正式结论必须使用固定测试集和真实 Pipeline 设置。
